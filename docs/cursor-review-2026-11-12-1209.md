# Cursor review · 2026-11-12 12:09

Review of the FleetPulse working tree after the screen move and the two sweep-defect fixes. Application code was not changed. Documentation that still described the old defects was updated in the same pass.

Checked the route store, reassignment handler, fleet snapshot merge, telemetry health, dispatcher socket, alert merge, HTTP client, and a search for raw HTML injection. Compared those paths with `docs/01-spec.md` and the 12 Nov sweep.

## Findings

### Medium · A route response that finishes after reset can restore the cleared list

`resetRoutes` bumps a generation and ignores an in-flight route read that loses that race. Route socket events and the create response do not consult the generation.

```46:48:src/screens/routes/hooks/useRoutes.ts
  const receiveEvent = useCallback((event: RouteEvent) => {
    setState(previous => mergeRouteEvent(previous, event));
  }, []);
```

A create, status, or reassignment response that resolves after `fleet_reset` calls `receiveEvent` or `acceptCreation` and merges that route back into the empty store. The refresh path has a second gap: it checks the generation before calling `setState`, not inside the updater, so a read that has already passed the check can still merge the pre-reset list.

`npm run test:e2e` covers a reset with no route write in flight. It does not cover this ordering. There is no unit test around the generation token.

### Low · A development reset does not restart live sensor state

Reset reloads the fleet snapshot through the same merge used for an ordinary refresh. Once a truck has a live receipt, that merge keeps the previous status, speed, fuel, and heading.

```95:104:src/screens/fleet/utils/telemetryHealth.ts
    next.set(truck.id, {
      ...previous,
      speed: previous.speed ?? baseline.speed,
      fuel: truck.fuel > 0
        ? { ...previous.fuel, value: previous.fuel.value ?? truck.fuel, zeroCount: undefined }
        : previous.fuel,
      engineTemp: previous.engineTemp ?? baseline.engineTemp,
      heading: previous.heading ?? baseline.heading,
      status: previous.status ?? baseline.status,
    });
```

The restarted mock can therefore stay hidden until the next telemetry tick, about two seconds later. Positions follow the newer timestamp, so the marker usually moves. `currentRouteId` comes from the new snapshot, so the cleared assignment does show. This is the normal refresh rule applied to a restart.

### Low · No automated coverage for two live reassignments of an active route

The mock now rejects a reassignment whose `If-Match` version is stale or whose source route is completed or cancelled. The mutation test covers the client's reading of that `409`. The browser check covers cancel, then a held reassignment. Two PUTs to different free trucks while the source stays active are still untested. The handler is synchronous, so the second request should see the incremented version. The gap is coverage, not a reproduced failure.

## Checked and not reported as defects

- Reassignment requires the reviewed version and refuses a terminal source route before it moves the truck. Status PATCH behavior is unchanged. This is a deliberate edit to the supplied mock.
- `fleet_reset` replaces the route list, clears peers and alerts, and reloads the fleet snapshot when no write is in flight. An ordinary snapshot still keeps routes that a late response omits.
- Alert text, route destinations, and notes render as React text. There is no raw HTML injection in `src/`.
- The mock accepts any `X-Dispatcher-Id` and allows any origin. The spec places production identity and authorization outside this assignment.
- A joined session still learns peers only from later messages. A leave can take ten seconds. Alerts stay in the tab, capped at 20. Those are the documented mock limits.
- `npx tsc --noEmit` completed with no errors during this review. The earlier `peers.map` squiggle does not reproduce against the current `DispatcherPresence` types.
